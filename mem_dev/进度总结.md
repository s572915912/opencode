## 一、项目目标

为 OpenCode 实现**工作记忆（Working Memory）**能力，解决长对话中因 compaction 机制导致的关键信息丢失问题。核心改进包括：

- 主动记忆刷写（Proactive Memory Flushing）
- 自动知识提取（Automatic Knowledge Extraction）
- 标识符保留（Identifier Preservation）
- 压缩后上下文恢复（Post-Compaction Context Recovery）
- 基础知识检索（Basic Knowledge Retrieval）

最终交付物：功能 Demo + 对比实验数据 + 分析报告。

## 四、首次实验（已作废 ❌）

> ⚠️ **本节记录的实验存在方法缺陷，结论已被修正。保留此节用于说明问题。**

### 问题所在

首次实验**未经过 OpenCode**，而是直接调用 DeepSeek API：

```
用户消息 → 直接调 DeepSeek API → 收到回复
           ⬆ 没有经过 OpenCode 的 session/compaction 流程
```

这导致两个致命问题：

1. **压缩方式不对**：用 Python 脚本模拟的压缩（"请总结以上对话"），与 OpenCode 的真实 compaction prompt 完全不同
2. **DeepSeek 缓存干扰**：DeepSeek API 有服务端前缀缓存（Prefix Caching），相同前缀的请求会命中缓存。全量上下文实验先跑，压缩实验后跑时，部分 token 可能已被缓存，导致分数偏高

### 错误结论（已废弃）

| 实验 | 分数 | ❌ 原错误结论 |
|------|------|-------------|
| 全量上下文 | 50.1% | — |
| 模拟压缩后 | 60.0% | "压缩后提升 +9.9%！说明好的压缩不丢信息" |

**这个结论是错的。** 压缩后分数提升是因为缓存 + 非真实压缩方式的共同影响。

### 500K 渐进压缩：消息数 vs Token 数触发策略

#### v1：按消息数触发（每 100 条压缩一次）

398 条用户消息，每 100 条触发 compaction，共 4 轮级联压缩：

| 对比 | Overall 得分 |
|------|:---:|
| 100K 单次压缩后 | 58.0% |
| **500K 四轮压缩后（按消息数）** | **29.0%** |

> ⚠️ 多轮压缩导致灾难性信息丢失：从 58% 暴跌至 29%。

#### v2：按 Token 数触发（128K 阈值）✅ 当前方案

**关键发现**：用户消息只占总 token 的 **12-15%**（助手回复占 85-88%）

| 来源 | user tokens | asst tokens | 总 tokens |
|------|:---:|:---:|:---:|
| 500K Cases | 64-77K | 331-390K | 408-459K |
| 1M Cases | 108-115K | 696-857K | 804-972K |

因此改为**按总 token 数**触发压缩，阈值 **128K**（匹配 OpenCode 真实 context window）：
- 遍历所有消息（user+assistant），仅注入 user 消息，但计入全部 token
- 500K Cases → **3 轮**压缩（@msg238, @msg487, @msg730 + 最终 1 轮 = 4 轮）
- 1M Cases → **6-7 轮**压缩

> 这比按消息数触发更真实——模拟了用户+模型共同填满 context window 的过程。

### 关键发现（基于 v2 三重评分）

#### 🔴🔴 时间推理损失最严重（-35.7%）

旧评分只显示 -9.5%，LLM Judge 精确判断后暴露真实损失：
- "4 weeks" 压缩后变 "2 weeks" → Judge=0.00（旧评分 KW=0.67 误判为部分正确）
- "21 days" 压缩后变 "17 days" → Judge=0.00（旧评分 KW=0.85 严重高估）
- **数字精度丢失是 Working Memory 第一优先级**

#### 🔴 知识更新下降（-13.5%）

"dashboard API 250ms" 压缩后变 "120ms"——具体数值被 compaction 覆盖。

#### ⚪ 信息提取变化不大（-0.7%）

v1 显示 -32.6%，但 LLM Judge 发现 "March 29, 2024" ≈ "March 29"，语义等价。旧评分因词汇不匹配而误判为大幅下降。

#### 🟢🟢 跨会话推理大幅提升（+33.2%）

"transactions 表加几列？" 压缩前 Judge=0.40，压缩后 Judge=1.00。结构化摘要整合了分散信息。

#### ⚠️ 事件排序始终很差（16~25%）

LLM Judge 比关键词更严格（Judge 给 event_ordering 10%~25%），确认这是 LLM 固有弱点。

## 六、🚀 突破性发现 — 全量消息注入（v4 新增）

### 问题根因

之前的实验只注入 **40 条** user 消息（BEAM Case 0 共 94 条），导致大量「知识更新」类信息被截断。GPT-5.4 的低分不是模型能力问题，而是数据不完整。

### 修复方法

去掉 40 条消息上限，注入**全部 94-100 条**用户消息。

### 对比结果（GPT-5.4, 2 Cases 平均）

| 指标 | 40条注入(旧) | 全量注入(新) | 提升 |
|------|:---:|:---:|:---:|
| **压缩前 Overall** | 24.3% | **52.2%** | **+28%** 🚀 |
| **压缩后 Overall** | 17.8% | **49.3%** | **+32%** 🚀 |
| knowledge_update 前 | 7.9% | **92.5%** | +85% 🏆 |
| knowledge_update 后 | 11.6% | **82.8%** | +71% 🏆 |
| multi_session 前 | 9.2% | **56.3%** | +47% 🏆 |

### 典型案例

| 问题 | 40条(旧) | 全量(新) | 原因 |
|------|:---:|:---:|------|
| "API response time?" | 0.00 | **0.90** | 250ms 信息在第 55 条消息 |
| "How many commits?" | 0.00 | **1.00** | 165 commits 在第 75 条 |

## 七、500K 多轮渐进压缩（v4 新增）

### 问题

100K split（~150K tokens/case）基本装得进 GPT-5.4 的 128K 上下文窗口，compaction 前后都能看到全部信息，无法真正测试压缩导致的信息损失。

### 解决方案

使用 **500K BEAM split**（~554K tokens/case），配合**多轮渐进压缩**：

```
注入 100 条 → compact 1 → 注入 100 条 → compact 2 → ... → 最终 probe
```

每轮 compaction 从 ~128K → ~5K 摘要，经过 3-4 轮**级联压缩**后：
- 最早的信息被反复蒸馏
- 测试的是**长期记忆存活率**，而非简单的摘要质量

### 数据集规模对比（tiktoken 实测）

| Split | Cases 数 | 每 case 总 tokens | user tokens | 128K 阈值压缩轮数 |
|-------|:---:|:---:|:---:|:---:|
| 100K | 20 | 52-213K | 10-35K | 0-1 轮 |
| **500K** | **35** | **408-459K** | **64-77K** | **3 轮 (+最终1轮)** |
| **1M** | **35** | **804-972K** | **108-115K** | **6-7 轮 (+最终1轮)** |

> ❌ BEAM 没有 5M 或 10M split（论文提到但 HuggingFace 未公开）。最大可用 split 为 1M。
>
> ⚠️ **各 split 的 Case 内容完全不同**（不是同一对话的不同长度版本）。100K Case 0 是"项目规划"，500K Case 0 是"Node.js 聊天 App"，1M Case 0 是"React+Node.js 全栈开发"。跨 split 的分数不能直接按 Case 对比。

## 十二、技术架构备注

### OpenCode 集成方式

```
Python 测试脚本
    │
    ├─ POST /session          → 创建会话
    ├─ POST /session/:id/message (noReply=true)  → 注入 BEAM 上下文
    ├─ POST /session/:id/message → 发送探测题 → DeepSeek 回复
    ├─ POST /session/:id/summarize  → 触发真实 compaction
    └─ POST /session/:id/message → 压缩后探测题
    │
    ▼
OpenCode Headless Server (port 4096)
    │
    ├─ Session CRUD + Message Store
    ├─ Compaction Prompt → 结构化摘要（Goal/Instructions/Discoveries/Accomplished/Files）
    └─ Provider Router → DeepSeek API
```

### 三重评分系统（v2 新增）

```
score_answer(question, model_answer, expected_answer)
    │
    ├─ score_keyword()     → 关键词重叠（Recall only）     权重 20%
    ├─ score_token_f1()    → SQuAD 式 Token F1（P+R）     权重 30%
    └─ score_llm_judge()   → DeepSeek 语义判断（0~1.0）   权重 50%
    │
    ▼ 融合逻辑：Judge ≥ 0.8 → 直接采信 Judge 分数
               Judge < 0.8 → 60% Judge + 25% F1 + 15% KW
```

优势：`"28 days"` vs `"4 weeks"` → KW=0.0, F1=0.0, **Judge=1.0**, Combined=1.0 ✅

# 实际发送: "[req-a3b8c1d2] When does my first sprint end?"
