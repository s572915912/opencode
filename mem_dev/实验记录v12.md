## 三、改动 1：PK 结构化模板

**V11 的 PK**：只有一个 `Key Facts & Values` 段，扁平列表。

**V12 的 PK**：拆成 6 个独立段落，各有不同用途：

```
## Persistent Knowledge (CRITICAL — accumulates across rounds, never discard)

### Value Registry (MOST CRITICAL — exact values only)
- key: EXACT value (e.g., "inference_time: 45ms", "python_version: 3.10")

### Chronological Event Log (preserve temporal order)
1. [date/context] First thing that happened
2. [date/context] Second thing that happened

### Contradiction & Update Log
- "X" was originally stated → later changed to "Y"

### Technical Specifications
- [identifier/category] exact value

### Causal Decisions
- Because [cause] → chose [action]

### User Preferences & Constraints
- [verbatim preference stated by user]
```

**为什么要拆**：V11 的扁平 `Key Facts` 里，精确数值和用户偏好混在一起，模型 compaction 时容易遗漏某些类型。拆成独立段后，每个段有明确的保留规则。

## 四、改动 2：Knowledge Gap Analysis（SK 知识补网）

在 compaction prompt 末尾新增 `## Knowledge Gap Analysis (Prediction-Correction)` 段：

```
## Knowledge Gap Analysis (Prediction-Correction)

After writing your Persistent Knowledge above, re-read the ORIGINAL conversation
and identify details NOT preserved in your summary.

ALWAYS extract these (even if mentioned in PK):
- [UPDATE] new_value (was: old_value) — EVERY value change
- [DECISION] chose X because Y — every decision with reasoning

Extract these ONLY if missing from PK:
- [FACT] exact value that was approximated or omitted
- [EVENT] event whose precise timing/ordering was lost
```

**原理**：让模型写完 PK 后"回头检查"，自我纠错补漏。类似 Prediction-Correction 的思想——先预测（写 PK），再校正（补 SK）。

---

## 五、改动 3：SK 持久化 + Theme 索引

SK（Structured Knowledge）条目持久化到 `.opencode/knowledge.jsonl`，每条格式：

```json
{"type":"fact","content":"integration_test_success_rate: 97%","ts":"2026-03-15"}
```

**Theme 索引**：SK 条目通过关键词聚类，生成 `.opencode/knowledge/` 目录下的主题文件：

```
.opencode/knowledge/
├── index.md                 ← 主题目录
├── kafka_upgrade_target.md  ← 按主题聚合的 SK 条目
├── api_gateway_timeout.md
└── ...
```

**上下文注入**：compaction 时，只展开与当前对话相关的 theme（通过关键词匹配），避免注入无关 SK。

## 六、改动 4：PK Append-Only Merge（核心改动）

### 问题

V11 的 `writePK()` 每轮 compaction 直接覆盖 `memory.md`。虽然有截断防护（段数检查），但模型每次输出相同段数、不同内容，防护从未生效。

**结果**：1M C2 经过 7 轮 compaction 后，早期关键事实全部丢失（`alphavantage.co/query`、`NUMERIC(10,2)`、`97%`、sprint 日期）。

### 解决方案

用 `mergePK()` 替代直接覆盖，按段落类型做不同合并策略：

| 段落 | 策略 | 增长控制 |
|:-----|:-----|:---------|
| Value Registry | 按 key 去重，old + new 合并，同 key 用新值 | 同 key 只保留一条 |
| Technical Specifications | 同上 | 同上 |
| User Preferences | 按内容去重 | 同上 |
| Contradiction Log | 按 key 去重 | 同上 |
| Causal Decisions | 按 key 去重 | 同上 |
| Chronological Event Log | 按编号合并去重 | 硬限 200 条 |
| 其他段落（Goal 等） | 用模型新输出 | 不累积 |

### 验证

修复后 1M C2 的 `memory.md`：94 行 → 534 行，6 个丢失的关键事实全部恢复。

## 七、改动 5：Paired 消息注入

V11 只注入 user 消息，assistant 回复仅用于计算 token 阈值。

V12 将 assistant 回复嵌入 user 消息一起发送：

```
[Previous Assistant Response]:
{assistant_content}

[User Message]:
{user_content}
```

**目的**：确保 compaction 模型能看到完整的问答上下文。

---

## 八、改动 6：顺序 Probe

V11 用并行 probe（每个问题独立 session）。V12 改为顺序 probe（同一个 session 逐条发送）。

**原因**：并行 probe 不符合真实用户交互场景。

**代价**：前面 Q&A 会影响后面的回答（上下文干扰）。
